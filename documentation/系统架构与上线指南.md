# 第 0 部分 · 你现在站在哪一步

先回答你的问题：**「我现在是在做后端还是在做 deployment？」**

答案是：**后端你基本做完了，现在这一步叫 deployment（部署），而且是 deployment 里最前面的那一小段。**

## 一个软件从想法到用户手上，要经过五层

| 层 | 中文 | 你在这层干什么 | 你的状态 |
| --- | --- | --- | --- |
| Product | 产品 | 想清楚做什么、给谁用、什么算做完 | ✅ 完成 —— 就是 `plan.txt` |
| Frontend | 前端 | 用户在浏览器里看到、点到的东西 | ✅ 完成 —— 7 个页面 |
| Backend | 后端 | 收请求、查数据库、调 AI、返回结果 | ✅ 完成 —— 5 个 router，约 1400 行 |
| Data | 数据层 | 数据长什么样、存在哪、怎么迁移 | ⚠️ 半成品 —— 表建好了，但没有 migration 机制 |
| Infrastructure / Deployment | 基础设施 / 部署 | 让这堆代码跑在别人的电脑上，7×24 不关机 | ❌ 没开始 —— 有两个配置文件，但没跑通过 |

**你现在的位置**：前三层能在你自己电脑上跑通了，第五层还是零。中间第四层有个坑（后面会讲）。

## 一个容易混淆的区分：DevOps、SRE、Platform、Deployment

这几个词经常混着用，面试和 JD 里都会出现：

- **Deployment（部署）** —— 一个**动作**。把代码放到服务器上跑起来。你现在要做的就是这个。
- **DevOps** —— 一种**文化 / 方法论**。核心主张是"写代码的人也要负责让它跑起来"，反对开发和运维分家。落地成果通常是 CI/CD 流水线。
- **CI/CD** —— DevOps 的具体工具。CI = Continuous Integration（持续集成，每次改代码自动跑测试）；CD = Continuous Deployment / Delivery（持续部署，测试过了自动上线）。
- **SRE**（Site Reliability Engineering，站点可靠性工程）—— Google 提出的职位。用软件工程的方法解决运维问题，关注"服务挂了几分钟"这类可量化指标。
- **Platform Engineering（平台工程）** —— 更新的说法。搭一套内部工具，让业务开发不用懂基础设施也能自助部署。

对你现在的规模：**你只需要 Deployment，加一点点 CI。** 其余的是团队上了规模才需要的。

# 第 1 部分 · 这个系统现在是什么样

## 一句话

一个**前后端分离的单体 Web 应用**：Next.js 前端跑在浏览器里，用 HTTP 和 WebSocket 跟一个 FastAPI 后端说话；后端把用户上传的图片先过一遍本地跑的深度估计模型，再连同图片一起发给 Claude，让 Claude 输出乐高零件清单和拼装步骤，结果存进 PostgreSQL。

这里面每个术语第 2 部分都会解释。

## 技术栈：每一样是干什么的

### 前端

| 技术 | 是什么 | 在这个项目里干什么 |
| --- | --- | --- |
| **Next.js 16** | React 的框架。React 只管画界面，Next 补上路由、打包、服务端渲染 | 提供 7 个页面的路由（`/`、`/upload`、`/chat` …） |
| **App Router** | Next.js 的新版路由方式，用文件夹结构决定 URL | `src/app/upload/page.tsx` → 网址 `/upload` |
| **React 19** | 界面库。把数据变成 HTML，数据变了自动重画 | 所有交互 |
| **Tailwind CSS v4** | 一种 CSS 写法，直接在标签上写 `className="flex gap-2"` 而不是另开样式文件 | 全部样式 |
| **Framer Motion** | 动画库 | 页面淡入、积木漂浮 |
| **react-dropzone** | 拖拽上传组件 | 上传页的拖拽区 |
| **TypeScript** | 加了类型检查的 JavaScript。写错变量名、传错参数，编译时就报错 | 全项目 |

**一个重要的现实**：你的 7 个页面**全部**是 `'use client'`，也就是全部在浏览器里执行。这意味着 Next.js 的服务端渲染能力你基本没用上，实际上更接近一个传统的单页应用（SPA）。这不是错，只是选型上值得知道 —— 它会影响 SEO 和首屏速度。

### 后端

| 技术 | 是什么 | 在这个项目里干什么 |
| --- | --- | --- |
| **FastAPI** | Python 的 Web 框架。收 HTTP 请求，返回 JSON。自带交互式 API 文档 | 全部 5 个路由模块 |
| **Uvicorn** | ASGI 服务器。FastAPI 只是框架，真正监听端口的是它 | 启动进程 |
| **SQLAlchemy 2（async）** | ORM，Object-Relational Mapper。让你用 Python 对象操作数据库，不用手写 SQL | `models.py` 定义 4 张表 |
| **asyncpg** | PostgreSQL 的异步驱动 | 实际连数据库的那一层 |
| **Pydantic** | 数据校验库。定义"请求应该长什么样"，不合格自动返回 422 | `schemas.py` |
| **python-jose** | 签发和验证 JWT | 登录发 token |
| **passlib + bcrypt** | 密码哈希。数据库里存的不是密码本身，是不可逆的哈希 | 注册和登录 |
| **WebSocket** | 一种和 HTTP 并列的协议。HTTP 是"问一次答一次"，WebSocket 是"连上就一直开着，双方随时能说话" | 聊天室、私信 |

### AI 部分

| 技术 | 是什么 | 在这个项目里干什么 |
| --- | --- | --- |
| **Depth Anything V2 Small** | 一个**单目深度估计**模型。给它一张普通照片，它猜出"哪里近、哪里远" | 把 2D 照片变成粗略的几何信息 |
| **Transformers** | HuggingFace 出的库，用来加载和运行开源模型 | 加载上面那个模型 |
| **PyTorch (torch)** | 深度学习框架。所有神经网络的底层运算靠它 | Transformers 的依赖，**部署最大的负担，第 3 部分详说** |
| **Claude (claude-sonnet-4-6)** | Anthropic 的大模型，能看图 | 把图片 + 深度数据变成乐高零件清单和步骤 |

## 数据模型：4 张表

```
users                      projects
├─ id (uuid)      ┌───────►├─ id (uuid)
├─ username(唯一) │        ├─ user_id ────┐
├─ email(唯一)    │        ├─ image_url   │ 外键，用户删了
├─ password_hash  │        ├─ s3_key      │ 作品级联删除
├─ avatar (emoji) │        ├─ result_json │ (乐高清单，JSONB)
└─ created_at     │        ├─ depth_data  │ (深度特征，JSONB)
                  │        └─ created_at  │
                  │                       │
                  └───────────────────────┘

friendships                messages
├─ id                      ├─ id
├─ requester_id ──► users  ├─ sender_id ────► users
├─ receiver_id  ──► users  ├─ receiver_id ──► users (私信才有，公聊为 NULL)
├─ status                  ├─ content (文本)
│  = pending | accepted    ├─ msg_type = public | dm
└─ created_at              └─ created_at
```

**JSONB** 是 PostgreSQL 的一种字段类型，可以直接塞一整个 JSON 进去还能被索引和查询。这里用来存 Claude 返回的零件清单 —— 因为结构可能变，不适合拆成固定的列。这是个合理的选择。

**一个设计缺口**：`friendships.status` 只有 `pending` 和 `accepted` 两个值，**没有 `rejected`（拒绝）**。但 `plan.txt` 的验收标准里写着"好友系统支持发送/接受/**拒绝**请求"。现在的实现里，拒绝只能靠 `DELETE /api/friends/{id}` 把整条记录删掉 —— 效果上能用，但对方可以立刻再发一次请求，没有"已被拒绝"的状态。**这是需求和实现对不上的地方。**

## 三条关键请求路径

### 路径 1：注册 / 登录

```
浏览器  POST /api/auth/login  { email, password }
   │
   ▼
后端    1. 按 email 查 users 表
        2. bcrypt 校验密码哈希
        3. 签发 JWT，内容是 { sub: user_id, exp: 7天后 }
   │
   ▼
浏览器  收到 { access_token, user }
        存进 localStorage 的 nebular_token / nebular_user
        之后每个请求都带 Authorization: Bearer <token>
```

### 路径 2：上传照片 → 出零件清单（核心功能）

```
浏览器  POST /api/images/upload   (multipart，一张图)
   │        │
   │        └─ 前端同时启动一个假进度条
   │           （upload/page.tsx:117 用 Math.random() 递增到 85% 就卡住，
   │            它和后端真实进度没有任何关系）
   ▼
后端    1. 校验类型（jpeg/png/webp/gif）和大小（≤15MB）
        2. 存图 → S3 或本地 ./uploads/
        3. 深度估计 —— 第一次调用要先加载模型，慢（30 秒起）
        4. 把图片 base64 + 深度数据一起发给 Claude
        5. 解析 Claude 返回的 JSON
        6. 写一条 projects 记录
        7. 一次性返回完整结果
   │
   ▼
浏览器  拿到零件清单 + 步骤，切到结果页
```

⚠️ **注意第 3、4 步是串行 `await` 的**（`images.py:35-41`），而且**整个过程都在同一个 HTTP 请求里**。代码注释写着 "run S3 upload and depth estimation in parallel"，但实际上并没有并行。冷启动时这一个请求可能要 **60 秒以上**。这是第 3 部分要决策的第二个问题。

### 路径 3：实时聊天

```
浏览器  new WebSocket("ws://后端/api/chat/ws/chatroom?token=xxx")
   │
   ▼
后端    1. 用 URL 上的 token 查用户
        2. 接受连接，加进内存里的连接列表
        3. 先推送最近 60 条历史
        4. 之后每收到一条消息 → 存库 → 广播给所有连接
```

# 第 2 部分 · 部署到底是什么

## 部署在解决什么问题

你在自己电脑上跑 `npm run dev` 和 `python run.py`，只有你自己能访问。部署要解决的是：

1. **有一台永远开着的电脑** —— 你的笔记本会合盖、会断网
2. **有一个别人能输入的地址** —— 不能是 `localhost`，要是 `nebular.app` 这种
3. **数据不能丢** —— 数据库要有备份，重启不能清空
4. **密钥不能写在代码里** —— API key 提交到 GitHub 就等于公开
5. **改了代码能安全更新** —— 而且更新时最好不要中断服务

## 平台的六大类别（行话对照）

这是你问的"这些平台属于什么类别"。理解了这六类，市面上所有云服务你都能归位。

### ① IaaS —— Infrastructure as a Service（基础设施即服务）

**你租到的是**：一台空的虚拟机。有 CPU、内存、硬盘、一个 IP 地址，装着一个干净的 Linux。

**你要自己干**：装 Python、装 Nginx、配防火墙、申请 HTTPS 证书、写开机自启、配日志轮转、打安全补丁……

**代表产品**：AWS EC2、Google Compute Engine、Azure VM、DigitalOcean Droplet、阿里云 ECS

**类比**：租一块毛坯地皮，自己盖房子。

**什么时候用**：需要极致控制、有特殊系统依赖、或者规模大到要自己优化成本。**你现在不需要。**

### ② PaaS —— Platform as a Service（平台即服务）

**你租到的是**：一个"你只管交代码"的环境。平台自动识别语言、装依赖、跑起来、配好 HTTPS 和域名。

**你要自己干**：写一个启动命令，填几个环境变量。**就这些。**

**代表产品**：**Railway**、**Render**、Fly.io、Heroku（PaaS 的鼻祖，现在贵了）、Google Cloud Run

**类比**：租一间精装修公寓，拎包入住。

**什么时候用**：几乎所有中小项目。**你的后端就该用这个 —— `railway.toml` 说明你已经选了 Railway。**

### ③ Serverless / FaaS —— Function as a Service（函数即服务）

**你租到的是**：连"服务器一直开着"这个概念都没有。你上传一个函数，有请求才启动，跑完就销毁，按毫秒计费。

**你要自己干**：把逻辑拆成一个个短小的函数。

**代表产品**：AWS Lambda、Vercel Functions、Cloudflare Workers

**类比**：不租房，按次数用共享办公桌。

**关键限制 —— 这条对你很重要**：
- 单次执行有**硬性时间上限**（Vercel 免费版 10 秒，付费 60 秒；Lambda 最长 15 分钟）
- 每次冷启动都要重新初始化，**不适合加载一个几百 MB 的深度学习模型**
- 没有常驻内存，**WebSocket 这种长连接跑不了**

👉 **所以你的后端不能放 Serverless。** 深度模型 + WebSocket 这两条，任意一条都判了死刑。这就是为什么后端要 Railway（PaaS）而不是 Vercel Functions。

### ④ 静态托管 / CDN —— Content Delivery Network（内容分发网络）

**你租到的是**：把编译好的 HTML/CSS/JS 复制到全球几十个机房，用户从最近的那个下载。

**代表产品**：**Vercel**、Netlify、Cloudflare Pages、GitHub Pages

**类比**：把你的传单印一万份，铺到全国每个便利店。

**什么时候用**：所有前端。**Vercel 是 Next.js 的亲爹（同一家公司），前端放这里是最省心的选择。**

### ⑤ 托管数据库 —— Managed Database

**你租到的是**：一个已经装好、配好、自动备份、自动打补丁的数据库，给你一根连接字符串。

**代表产品**：Railway Postgres、**Supabase**、**Neon**、AWS RDS、PlanetScale

**类比**：不自己养奶牛，直接订牛奶。

**为什么强烈建议用托管的**：数据库是整个系统里**唯一丢了就真的没了**的部分。自己运维数据库要处理备份、故障恢复、版本升级、连接池，这些每一项做错都可能导致数据永久丢失。

### ⑥ 对象存储 —— Object Storage

**你租到的是**：一个专门存文件的无限大硬盘，每个文件有个 URL。

**代表产品**：**AWS S3**（这类服务的事实标准）、Cloudflare R2（不收流量费）、Backblaze B2

**为什么不能存在服务器硬盘上**：PaaS 平台的硬盘是**临时的（ephemeral）**。每次重新部署，容器重建，硬盘清空 —— **用户上传的照片全部消失**。

👉 你的代码里 `USE_S3=false` 时会写到 `backend/uploads/`。这在本地没问题，**部署上去就是个定时炸弹**。

## 你这个项目需要哪几类

| 需要什么 | 类别 | 推荐 | 为什么 | 大概费用 |
| --- | --- | --- | --- | --- |
| 前端 | 静态托管 / CDN | **Vercel** | Next.js 官方平台，`git push` 自动部署 | 个人项目 $0 |
| 后端 | PaaS | **Railway** | 你已经配好了；能跑长进程和 WebSocket | 约 $5/月起 |
| 数据库 | 托管数据库 | **Railway Postgres** 或 **Neon** | Railway 的和后端在同一个项目里，内网连接；Neon 有更慷慨的免费额度 | $0–5/月 |
| 存图片 | 对象存储 | **Cloudflare R2** 或 **AWS S3** | R2 不收流量费，对图片站更省 | 几乎 $0 |
| 大模型 | 外部 API | **Anthropic API** | 已接好 | 按用量，每次分析约 $0.01–0.03 |
| 代码托管 + CI | 代码平台 | **GitHub + Actions** | 已经在用 | 公开仓库免费 |

**合计：一个月 $5–10 能跑起来。**

## 一次标准的部署流程长什么样

```
你在本地改代码
      │
      ▼
git push origin main
      │
      ├──────────────► GitHub Actions (CI)
      │                 跑测试、跑类型检查、跑 lint
      │                 ❌ 挂了就停在这，不往下走
      │                 ✅ 过了继续
      │
      ├──────────────► Vercel 检测到 push
      │                 npm run build → 部署前端
      │                 给你一个预览链接
      │
      └──────────────► Railway 检测到 push
                        装依赖 → 启动 uvicorn
                        调 /health 确认活着
                        ✅ 健康 → 切流量到新版本
                        ❌ 不健康 → 自动回滚到旧版本
```

这套东西的名字就叫 **CI/CD 流水线（pipeline）**。你现在一条都没有 —— 没有 `.github/workflows/`，也没有测试。

## 几个你一定会遇到的行话

| 术语 | 意思 | 在你项目里的体现 |
| --- | --- | --- |
| **环境变量 / env var** | 不写死在代码里、由运行环境注入的配置。密钥必须走这个 | `backend/.env`、`DATABASE_URL`、`ANTHROPIC_API_KEY` |
| **环境（environment）** | 同一套代码的不同副本：dev（本地）/ staging（预发，给自己测）/ production（生产，给用户） | 你现在只有 dev |
| **健康检查 / healthcheck** | 平台定期访问一个地址，不通就认为服务挂了、自动重启 | 你有 `/health`，`railway.toml` 已配 |
| **冷启动 / cold start** | 服务从零启动到能响应第一个请求的时间 | 你的深度模型第一次加载 30 秒+ |
| **迁移 / migration** | 用版本化的脚本改数据库结构，可回滚、可重放 | ⚠️ **你没有** —— 用的是启动时 `create_all` |
| **回滚 / rollback** | 新版本出问题，切回上一个版本 | Vercel / Railway 都自带 |
| **CORS** | 浏览器的安全策略：网页只能请求同源地址，除非服务器明确放行 | `config.py:allowed_origins`，上线后必须加上 Vercel 域名 |
| **反向代理 / reverse proxy** | 挡在应用前面的一层，负责 HTTPS、限流、负载均衡 | Railway 自带，你不用管 |
| **水平扩展 / horizontal scaling** | 加机器而不是换更大的机器 | ⚠️ **你现在做不到**，原因见下 |

⚠️ **一个必须知道的限制**：你的 WebSocket 连接列表存在**进程内存**里（`app/ws/manager.py`）。这意味着一旦你在 Railway 上把实例数从 1 调到 2，连在 A 实例的用户和连在 B 实例的用户**互相收不到消息**。要真正支持多实例，需要引入 Redis 做消息广播（术语叫 **Pub/Sub**）。在你的用户量下，**保持单实例就行**，但要知道这是天花板。

# 第 3 部分 · 两个待决策的技术问题

这两个问题你之前说"没太懂"，这里从头讲。

## 决策 A：深度模型（torch）怎么办

### 背景：这三个东西是什么关系

- **PyTorch（`torch`）** —— 深度学习框架，所有神经网络计算的底层。它很大，因为要包含 GPU 加速代码。
- **Transformers** —— HuggingFace 的库，负责下载和运行现成的开源模型。它依赖 PyTorch。
- **Depth Anything V2 Small** —— 具体那个模型。参数文件约 100 MB。

### 问题出在哪

你的 `requirements.txt` 里写的是：

```
torch==2.5.1
```

`pip install torch` 默认装的是 **CUDA 版本** —— 也就是包含 NVIDIA 显卡加速代码的版本，**约 2.5 GB**。

但你的代码里明确写着 `device="cpu"`（`app/services/depth.py:32`）—— 你根本不用 GPU，那 2.5 GB 里的绝大部分是**你永远不会执行的代码**。

**后果**：Railway 构建时要下载并解压这 2.5 GB。免费额度大概率超时或内存不足，构建直接失败。**这是你部署路上第一个会撞上的墙。**

### 三个选项

| | 选项 1：CPU 版 torch | 选项 2：关掉深度估计 | 选项 3：换轻量算法 |
| --- | --- | --- | --- |
| **怎么做** | requirements 指向 PyTorch 的 CPU 专用源，体积从 2.5GB 降到约 200MB | 生产环境设 `ENABLE_DEPTH_ESTIMATION=false`，图片直接给 Claude | 用 Pillow + numpy 算边缘密度、明暗梯度，近似出几何复杂度 |
| **保留真实深度估计** | ✅ 是 | ❌ 否 | ❌ 否（是近似） |
| **镜像大小** | ~800MB | ~150MB | ~150MB |
| **运行内存** | ~1GB（模型常驻） | ~200MB | ~200MB |
| **Railway 费用** | Hobby 档 $5/月 | 免费档可能够 | 免费档够 |
| **冷启动** | 首次请求 +30 秒 | 无额外开销 | 无额外开销 |
| **对简历的价值** | ✅ 高 —— "本地跑视觉模型"是真本事 | ❌ 低 —— 变成纯 API 调用 | 🔸 中 —— 展示了 CV 基础 |
| **改动量** | 小（改 requirements + 加 Dockerfile） | 极小（改一个环境变量） | 中（重写 depth.py） |

**我的建议：选项 1。**

理由：深度估计是这个项目**唯一的技术护城河**。去掉之后，它就退化成"上传图片调一次 Claude"，任何人一小时能复刻。多花 $5/月保住它，值得。而且 CPU 版 torch 这个改法很小，就是换个 pip 源。

顺带一提：代码里已经有一个很好的设计 —— `estimate_depth()` 出任何错都会返回 `{"error": ..., "fallback": True}` 而不是崩溃，`analyze_image()` 在没有 API key 时会返回 `MOCK_RESULT`。**这叫优雅降级（graceful degradation）**，是加分项，文档里值得写出来。

## 决策 B：上传流程要不要改成异步

### 背景：同步 vs 异步

**同步（现在的做法）**：

```
浏览器 ──── POST /upload ────────────────────────────► 后端
                                                        │ 存图 (1s)
       （浏览器一直等，转圈圈，什么都干不了）              │ 深度估计 (5-30s)
                                                        │ 调 Claude (20-40s)
       ◄──────────── 完整结果 ──────────────────────────┘
       整个过程 30-70 秒，一根 HTTP 连接从头挂到尾
```

**异步（任务队列模式）**：

```
浏览器 ──── POST /upload ──► 后端：存图，建一条 pending 记录
       ◄─ 202 + project_id ─┘   （1 秒内返回，连接断开）
                                 后台开始干活 ↓
       ──── GET /status/{id} ──► "processing, 深度估计中"
       ──── GET /status/{id} ──► "processing, AI 分析中"
       ──── GET /status/{id} ──► "done" + 完整结果
       （每 2 秒问一次，这叫轮询 / polling）
```

### 为什么这不只是"好看一点"

1. **网关超时**。云平台的负载均衡器对单个 HTTP 请求有时间上限。Railway 大约 5 分钟，还算宽松；但如果你以后想在前面加 Cloudflare（默认 100 秒）或换到 Vercel Functions（60 秒），**同步方案直接不能用**。
2. **你的 README 已经这么写了**。文档里写着 `GET /api/images/status/{project_id}` 是"poll one build for progress"（轮询查看进度）。但看代码，`upload` 已经把所有结果返回了，`status` 只是查一条已完成的记录 —— **文档描述的架构和实际代码不一致**。
3. **进度条现在是假的**。`upload/page.tsx:117` 用 `Math.random() * 8` 递增到 85% 就停住，跟后端一点关系都没有。用户看到 85% 卡住，不知道是在跑还是死了。
4. **重试无从谈起**。现在 Claude 调用失败会静默返回 mock 数据（`bricks.py:178`），用户拿到一个假清单却以为是真的。有了任务状态，才能诚实地说"分析失败，点击重试"。

### 两个选项

| | 选项 1：改成异步 202 + 轮询 | 选项 2：保持同步，只加超时和真实提示 |
| --- | --- | --- |
| **后端改动** | `upload` 立即返回 → 用 FastAPI `BackgroundTasks` 或独立 worker 跑分析 → `projects` 加 `status`、`error` 字段 | 加请求超时、把 Claude 失败真实报错而不是返回 mock |
| **前端改动** | 上传页重写：轮询 `/status`，显示真实阶段 | 保留假进度条，加超时提示和重试按钮 |
| **数据库改动** | 需要（加字段 → 需要 migration） | 不需要 |
| **工作量** | 中等（1–2 天） | 小（2–3 小时） |
| **能扛住网关超时** | ✅ | ❌ |
| **和 README 一致** | ✅ | ❌ 需要改 README |
| **对简历的价值** | ✅ 高 —— 任务队列是后端核心能力 | 🔸 低 |

**我的建议：选项 1，但用最简单的实现。**

不需要上 Celery + Redis 那套重型方案（那是给每天几万任务的系统用的）。FastAPI 自带的 `BackgroundTasks` 就够 —— 请求返回后继续在同一个进程里跑。**代价是进程重启会丢失进行中的任务**，但对你的规模完全可以接受，而且以后要换成真队列，接口形状不用变。

这个模式的行话叫 **异步任务模式（async job pattern）**，或者按 HTTP 语义叫 **202 Accepted 模式**。

# 第 4 部分 · 上线前必须修的问题

这份清单来自实际读代码。**按严重程度排序**，标 🔴 的不修就上线会出事。

## 🔴 严重：不修不能上线

### 1. 公开聊天室允许匿名冒充任何人

`app/routers/chat.py:79` —— WebSocket 握手时 `_resolve_ws_user(token)` 返回 `None` 也照样接受连接。之后进入 guest 分支（`chat.py:117`），消息的用户名和头像**直接取自客户端发来的 JSON**：

```python
"sender_username": data.get("username", "Guest"),
"sender_avatar": data.get("avatar", "⚪"),
```

**攻击者能干什么**：不用注册，直接连 WebSocket，把 `username` 填成任意已有用户名，冒充别人在公开聊天室发言。虽然这类消息不入库，但会实时广播给所有在线用户。

**怎么修**：要么公聊也要求登录（和 `plan.txt` 写的"用户需注册登录才能使用核心功能"一致），要么强制给 guest 打上无法伪造的标记（比如用户名固定为 `游客#随机数`，并在前端明确区分展示）。

### 2. 前端硬编码了 `http://localhost:8000`

`src/app/upload/page.tsx:149`：

```typescript
const displayImage = imageUrl
  ? (imageUrl.startsWith('/static/') ? `http://localhost:8000${imageUrl}` : imageUrl)
  : preview;
```

**后果**：部署后如果 `USE_S3=false`，所有分析结果里的图片都指向用户自己电脑的 8000 端口 —— 全部裂图。

**怎么修**：改用 `NEXT_PUBLIC_API_URL`。**更好的做法是生产环境一律开 S3/R2**，这条路径就不存在了。

### 3. `SECRET_KEY` 有默认值，生产环境不会报错

`app/config.py:7` —— 默认值是 `"change-this-in-production"`。如果部署时忘了设这个环境变量，服务照常启动，但**任何人都能用这个公开的默认密钥伪造 JWT，登录成任意用户**。

**怎么修**：启动时检查 —— 生产环境如果 `SECRET_KEY` 还是默认值，**直接拒绝启动**。宁可部署失败，也不要带着这个洞上线。

### 4. `torch` 会让 Railway 构建失败

见第 3 部分决策 A。

### 5. 登出没有清除 token

`src/components/Navbar.tsx:19` —— `handleLogout` 只删了 `nebular_user`，**`nebular_token` 还留在 localStorage 里**。

**后果**：用户点了"退出登录"，界面上看起来退出了，但 token 仍然有效（7 天过期）。共用电脑上，下一个人手动恢复 `nebular_user` 就能继续用这个账号。

**怎么修**：一行的事 —— 把 `nebular_token` 也删掉。

## 🟠 重要：上线后很快会出问题

### 6. 没有数据库迁移机制

`database.py:init_db()` 用的是 `Base.metadata.create_all` —— 它只会**创建不存在的表**，**永远不会修改已存在的表**。

**后果**：以后你给 `projects` 加一个 `status` 字段（决策 B 就需要），本地删库重建没问题，**线上那张表永远不会变，代码一查这个字段就 500**。

**怎么修**：启用 alembic（`requirements.txt` 里已经装了，只是没用）。这是数据库版本控制的标准工具。

### 7. 用户上传的照片会发给 Anthropic

`app/services/bricks.py:143` 把图片 base64 后发给 Anthropic API。这是功能的必要部分，**但目前没有在任何界面上告诉用户**。

**怎么修**：上传页加一句说明。如果以后有欧洲用户，这是 GDPR 的合规要求。

### 8. 没有任何限流

所有接口都没有速率限制。`/api/images/upload` 每次调用都会消耗你的 Anthropic 额度（每次约 $0.01–0.03）。**一个脚本循环调用就能刷爆你的账单。**

**怎么修**：至少给上传接口加限流（比如每用户每小时 10 次）。`slowapi` 是 FastAPI 生态常用的库。

### 9. 本地磁盘存储在 PaaS 上会丢文件

见第 2 部分对象存储那节。**生产环境必须 `USE_S3=true`。**

### 10. N+1 查询

`friends.py:103` 和 `chat.py:48` 都在循环里逐条 `await db.refresh(...)`。查 50 个好友就发 50 次额外查询。

**行话**：这叫 **N+1 查询问题** —— 1 次查列表，然后 N 次查每一项的关联数据。

**怎么修**：用 SQLAlchemy 的 `selectinload()` 一次性把关联数据查出来。
