# 权限模型

## 角色

系统**只有两种主体**，没有角色字段、没有管理员概念：

| 主体 | 判定方式 | 说明 |
| --- | --- | --- |
| **已认证用户** | 携带有效 JWT | 全部用户权限完全相同 |
| **匿名访客** | 无 token 或 token 无效 | 理论上只能读公开聊天记录，实际能做的更多（见下） |

`users` 表**没有 `role`、`is_admin` 之类的字段**（`models.py:13`）。没有后台管理界面，没有内容审核能力，没有封禁机制。运维只能直接操作数据库。

## 权限推导

所有授权判断都是**代码里的显式比较**，没有用数据库层的行级安全（RLS）。归结为三种模式：

1. **归属检查** —— `resource.user_id == current_user.id`
2. **参与方检查** —— `current_user.id in (friendship.requester_id, friendship.receiver_id)`
3. **好友关系检查** —— 存在 `status == "accepted"` 的 `Friendship`

## 唯一的权限缺口

🔴 **公开聊天室的写入没有认证**（`chat.py:79-135`）。

- WebSocket 握手不校验 token 有效性
- 游客消息的 `sender_username` / `sender_avatar` 由客户端自行提供并原样广播
- 结果：任何人可冒充任意已注册用户在公开频道发言

其余所有接口的授权检查都是正确的。特别值得肯定的是私信路径 —— 它在 WebSocket 握手阶段就完成了认证和好友关系双重校验，这是很多项目会漏掉的地方。

## 缺失的能力（不是漏洞，是尚未实现）

| 能力 | 影响 |
| --- | --- |
| 无内容审核 / 举报 / 封禁 | 公开聊天室出现滥用无处置手段 |
| 无消息删除 | 发出去的消息任何人都无法删除，包括发送者 |
| 无账号删除 | 用户无法自主删除数据（GDPR 场景下是合规问题） |
| 无资料修改接口 | 用户名、头像、密码注册后不可更改 |
| 无令牌吊销 | 改密码或登出无法使已签发的 JWT 失效，最长 7 天窗口 |
| 无屏蔽 / 拉黑 | 删除好友后对方可立即重新发起请求 |
